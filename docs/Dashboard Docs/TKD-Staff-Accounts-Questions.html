Admin "Reset password" — questions before the mockups

All five answered 2026-10-17 by Jeffrey · each answer goes into the rulebook (10b row + changelog). Nothing is built until the mockups are approved and you OK the build.

Why this is needed now

  • The rulebook (v0.16, §5) says: no self-service reset link; the sign-in screen says "Forgot password? Ask an admin to reset it."; admins reset it from Staff accounts (§6, account menu → Admin).
  • Staff accounts doesn't exist yet (v0.28: "designed when personal logins arrive"). So today "ask an admin" means the admin pastes the SQL snippet in supabase/SETUP.md ("Change the desk's password", Option 2). That works but is error-prone: a typo in the UID, the password sitting in the SQL Editor's history, no change-log entry.
  • The front-desk account (shared, v0.27/v0.28) can't change its own password in the app, so every desk password problem lands on an admin.

Already fixed by earlier decisions (not questions)

  • Minimum 12 characters (v0.28, Supabase setting) — the reset enforces the same rule.
  • Admins only, and only from an unlocked, recent admin session (is_admin() and has_data_access(), handoff §6).
  • An admin can't reset their own password here — they use Change password (it asks for the current one). Same rule as admin_set_staff_pin.
  • An admin can reset the other admin (Jeffrey ↔ grandmaster), so one admin who forgets is never locked out (v0.23).
  • Every reset is written to the change log (who, when, whose password) — never the password itself.
  • Icon map (§2.4) already has ti-user-cog (Staff accounts), ti-password (password), ti-key (PIN).

Question 2 — Where does the "set someone else's password" code run? Answered: A — database function (v0.71)

The browser app can't do it: setting another user's password is an Auth "admin" power, and the key that grants it (service_role / secret key) must never be in the app (handoff §6). So something on a server must do it. I checked the live project (read-only): the database's owner role is allowed to update auth.users and delete from auth.sessions / auth.one_time_tokens — the same thing the SETUP snippet does today.

A. A database function (security definer) Recommended

App
admin's own loginadmin_reset_password()
in Postgresauth.users
new bcrypt hash

A new function in migration 0004, same pattern as admin_set_staff_pin: checks admin + unlocked + recent password, refuses your own account and anything under 12 characters, stores the password as a bcrypt hash (exactly what Supabase Auth does), signs the person out and cancels emailed links — all in one all-or-nothing step — and writes the change log.

  • No secret key anywhere. Nothing new to deploy or keep secret.
  • One place for the security rule, tested with the existing PGlite tests like 0002/0003.
  • Works in local preview (fake database) and on the real one the same way.
  • Writes Supabase's own Auth tables directly. Supabase documents those tables as theirs and they "may change". If Supabase renames a column or stops allowing it, the function fails with an error (it can't silently half-work: one statement, all or nothing). The fix then is option B.
  • Supabase's own password extras (leaked-password check — Pro plan only, not on yet; "password changed" email) don't run for this path.

B. Cloudflare Pages Function with the secret key

App/api/reset
Cloudflare secret keySupabase Auth API

A small server function in the dashboard's Cloudflare project. It checks the caller is an admin (by asking the database with the caller's own login), then calls Supabase's official admin API with the secret key stored as a Cloudflare secret.

  • Uses Supabase's supported API — won't break if Auth's tables change.
  • The full-power secret key lives in Cloudflare. If that function has a bug, the key can do anything to the database. v0.33 rejected this for the public form for that reason.
  • The admin API doesn't sign the person out everywhere by itself — needs extra calls. Two pieces to keep in sync (function + database check). Can't be tried in local preview without extra setup.

  • Key stays inside Supabase.
  • Still the full-power key in code; a second deploy target with its own tooling. Rejected for the same reasons in v0.33.

Question 3 — What else happens when a password is reset? Answered: A — sign out + cancel links (v0.72)

A. Sign out everywhere + cancel emailed links Recommended

Password reset for Staff. Signed out on 3 devices.

Same as the SETUP snippet: new password set, any password-reset / magic-link email already sent stops working, and every device signed in as that person goes back to the sign-in screen (within about a minute; the database refuses them at once).

  • A reset is usually "someone shouldn't have this password" — this is the only version that actually locks them out.
  • Matches the rulebook's Change password (v0.28: it signs out other devices).
  • For the desk: every desk device needs the new password typed in once (and the PIN after). Say so in the confirmation.

B. Just change the password

Password reset for Staff.

Devices already signed in stay signed in (until their 7-day password rule).

  • No interruption at the desk.
  • Someone who knew the old password and is signed in somewhere keeps access for up to 7 days. Emailed links keep working.

Question 6 — What does "Reset PIN" do? Answered: B — admin sets the new PIN (v0.75)

Came up while planning the mockups: v0.28 said an admin reset clears the PIN (the person picks a new one at next sign-in), but admin_set_staff_pin and the SETUP snippet set a specific PIN.

A. Clear it; they choose their own

Matches v0.28. Desk devices already signed in have no PIN, so the next lock signs them out; the first person in picks the desk PIN.

B. Admin sets the new PIN Chosen

Admin types the 4 digits (weak PINs refused) and tells them. Works on every device at once; no one is signed out. Uses the existing admin_set_staff_pin.

C. Both: shared B, personal A

Two flows; no personal logins yet. Can be added later.
