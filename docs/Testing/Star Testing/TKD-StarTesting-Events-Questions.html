Star testing · Events tab — design questions

Jae H. Jeong's U.S. Taekwondo Center · Star testing · guidelines v0.68 · October 17, 2026 · One question at a time. Answered questions stay in this file with their answer.

Design only — not a working app. Event names, dates and counts are examples. These are option sketches for one decision (PC and phone only); the full Events tab mockups (PC, tablet, phone, every state, touch dialogs) come after the questions are answered. Amber text = proposed, not decided.

The Events tab is the first tab of Star testing: every star testing event, upcoming and past, with “+ Add event” in the page header. Clicking an event opens its own page (Candidates · Grading · Results). Already decided and drawn this way: joint event, works on Both (v0.58); columns name, date, candidate count and one status tag (v0.60); each event copies the rubrics and prices when it is created (v0.61); the add button sits in the page header (v0.45).

Question 1 — How does registration open and close?

Answered 2026-10-17: Option C, with the label shortened to “Registration”

Recorded in the rulebook as v0.67, including the details drawn and described under Option C: new events start Closed; the closing date starts ticked at 7 days before testing; it never reopens anything; reopening after the date removes it; ⋯ Close / Open registration with Undo; the date is shown openly (exception to rule 8). The Option C drawing below shows the new label.

Families register with the event's link (no login, v0.33). The dashboard needs a rule for when that link accepts sign-ups. Proposed, decided with the public form: a closed link shows a short page such as “Registration for Winter 2027 Star Testing is closed. Please ask the front desk.”, and staff can add a walk-in candidate themselves from the Candidates tab.

Option A — A switch you flip

What it does

  • Each event has one Open | Closed switch in Add event / Edit event. New events start Closed, so the family link never works before you're ready.
  • You open it when you hand out the link, and close it yourself when sign-ups should stop.
  • Quick open / close without the dialog: the event's ⋯ menu has Close registration (or Open registration). It happens at once with a 5-second Undo toast (rule 1.4: reversible, so no confirmation). Drawn open on the phone frame. Edit event shows the same switch.
  • Events list tag: Registration open (green) or Registration closed (gray).

Good

  • Simplest to understand: what the switch says is what families get.
  • Close early or reopen for a late family in two taps (⋯ → Open registration).

Bad

  • Depends on someone remembering to close it. A forgotten switch means families keep signing up after the cut-off, possibly the night before testing.
  • No deadline is known to the dashboard, so the family form can't show one.

Option B — Automatic opening and closing dates

What it does

  • No switch. Each event has two dates: Registration opens and Registration closes. The link opens at the start of the first day and closes at the end of the second (11:59 PM, Massachusetts time), all by itself.
  • Events list tag: Opens Jan 4 (gray) before the window, Open until Nov 7 (green) during it, Registration closed (gray) after.
  • Both dates must be on or before the testing date, and opening before closing (“The closing date must be on or before the testing date.”).

Good

  • Fully automatic: set it once when the event is created and nobody has to remember anything.
  • You can set an event up months early; the link stays shut until the opening date.
  • The family form can show the deadline (“Register by Sat, Feb 6”).

Bad

  • Exceptions are roundabout: to close early you move the closing date to today; to let one late family in you move it forward, then remember to move it back.
  • Two dates to fill in on every event, even when you just want “open now”.

Option C — A switch plus an optional closing dateRecommended

What it does

  • The Open | Closed switch from Option A, plus an optional closing date (“Close automatically at the end of …”). New events start Closed.
  • Proposed defaults: the box starts ticked, with the date set to 7 days before the testing date. Change the date or untick it freely; unticked, the event behaves exactly like Option A.
  • When the date passes, registration closes by itself (end of that day, 11:59 PM Massachusetts time) and the change log records it (“Closed automatically at the end of Feb 6”). The date never reopens anything.
  • Reopening after the date has passed removes the date (otherwise it would close again at once). The toast says so: “Registration open. The automatic closing date was removed. · Undo”.
  • The date must be on or before the testing date (“The closing date must be on or before the testing date.”).
  • Quick open / close without the dialog: the event's ⋯ menu has Close registration (or Open registration). It happens at once with a 5-second Undo toast (rule 1.4: reversible, so no confirmation). Drawn open on the phone frame. Edit event shows the same switch.
  • Events list tag: Open until Nov 7 (green) when a date is set, Registration open when not, Registration closed (gray).

Good

  • Set an event up early and keep it quiet (starts Closed).
  • The deadline enforces itself and can be shown to families, yet closing early or reopening for a late family is still two taps.

Bad

  • Two controls instead of one: slightly more to explain to staff.
  • Opening is never automatic: someone opens it by hand when the link goes out (that's the trade against Option B).
  • Small extra build work: the website checks the date whenever a family opens the link. Nothing needs to run overnight.

Note

  • Rule 8 puts optional fields under “More details”. The closing date is shown openly here on purpose, because it's on by default; if you choose C, that's recorded as a deliberate exception.

Recommendation: Option C

Star testing happens a few times a year, so the cost of opening by hand once per event is small, while a deadline that enforces itself matters more (a forgotten switch, Option A's weakness, is the likeliest real mistake). C also keeps the everyday exceptions, closing early or letting one late family in, to two taps; with B they mean editing dates. Choose B instead if you want to set events up far ahead and never touch them again. Choose A if you want the dialog as simple as possible and trust whoever runs the event to close it.

Blue count: the Events page uses 5 blue elements (Testing rail icon, Both, ← Testing, Add event, Events tab). Inside the dialog the page behind is dimmed, so the dialog's Save, selected switch and checkbox are counted on their own. Any future blue on the list (for example a “Copy family link” link) would go over the limit and needs another look.

Question 2 — Who can add and edit events, and open or close registration?

Answered 2026-10-17: Option C

Admins add and edit events and open or close registration any time. Staff can close registration any time and reopen it only before the closing date; after it, “Open registration” is grayed out with “The closing date has passed. Ask an admin to reopen.” Enforced in the database. Recorded in the rulebook as v0.68.

The dashboard has two account levels, Admin and Staff (v0.15); the shared front-desk account is Staff (v0.27). For Rubrics and prices you chose Admin edits, Staff view only (v0.61). This question is the same choice for events. Below, every frame is what a Staff account sees; the admin view is Question 1's.

Option A — Admin only; staff view

What it does

  • Admins add events, edit them, and open or close registration. Staff (including the shared front-desk account) see the Events list read-only: no “+ Add event”, no Edit icon, no ⋯ menu, and a gray line “View only. Ask an admin to add or change events.” Phone rows show a chevron instead (the row opens the event).

Good

  • Same rule as Rubrics and prices (v0.61): one simple rule for the whole Star testing setup.
  • Nobody at the desk can change an event by accident.

Bad

  • A late family at the desk, or closing registration early, needs an admin to be reached (the desk account can't do it). The desk can still add the candidate by hand if the Candidates tab allows staff to (decided later).

Option B — Admin adds and edits; staff can open or close registrationRecommended

What it does

  • Admins add and edit events. Staff get one thing: the ⋯ menu with Close registration / Open registration (instant, 5-second Undo, logged — as “Staff” for the desk account, v0.27). No “+ Add event”, no Edit icon. Gray line: “Ask an admin to add or change events.”
  • If staff reopen after the closing date has passed, the date is removed (v0.67) — staff can do that, and it's in the change log.

Good

  • The everyday exception (let a late family in, or stop sign-ups early) is handled at the desk in two taps.
  • Event name and date stay admin-only.

Bad

  • Staff can override the admin's deadline: reopening after the closing date removes that date (v0.67).
  • Anyone at the desk can reopen registration; on the shared account you'd only see “Staff” in the log, not who.
  • A rule with an exception: slightly more to explain, and one more database rule to build and test.

Option C — Like B, but staff can only reopen before the closing date

What it does

  • Same as B, with one limit: staff can close registration any time, but can reopen it only while the closing date hasn't passed. After the date, ⋯ shows “Open registration” grayed out with the reason under it: “The closing date has passed. Ask an admin to reopen.”
  • No closing date set → staff can open and close freely, as in B.

Good

  • The admin's deadline can't be undone at the desk; staff can still stop sign-ups early.

Bad

  • The late-family-after-the-deadline case, the main reason for B, still needs an admin.
  • The most rules to explain: what staff can do depends on the date.

Option D — Staff add and edit events too

What it does

  • Staff and admins can both add events, edit them (name, date, closing date) and open or close registration. Staff screens look exactly like the admin's. (Deleting is Question 6, so it may still be admin only.)

Good

  • No bottleneck: whoever runs the event can set it up.
  • Simplest screens: one version for everyone.

Bad

  • Anyone at the shared desk could rename an event, move its date, or create a stray event; the log shows only “Staff”.
  • Different from Rubrics and prices (admin only), so Star testing would have two rules.

Recommendation: Option B

The one thing the desk realistically needs on testing week is to let a late family in or stop sign-ups, and B gives exactly that while keeping the event itself (name, date, deadline) with admins, matching Rubrics and prices. Choose A if you'd rather every change to an event go through an admin. Choose C if a deadline an admin set should never be undone at the desk. Choose D only once staff have personal logins, so the log shows who did what.
