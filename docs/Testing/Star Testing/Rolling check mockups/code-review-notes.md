## SHOULD
1. **Make-up Undo can silently delete grades entered in the 5 seconds.** `CandidatesTab.jsx:1097` calls `deleteCandidate({ expectedVersion: newVersion, expectedPaymentIds: [] })`. The database only checks the candidate version and payment ids (`0006_star_testing.sql:4650-4656`), and grade / count saves never bump the candidate version and have no version check (0006 lines 510, 747, 5086, 5188). So if an admin enters a grade (Grading tab) on the new make-up row inside the toast's 5 seconds, then taps Undo, the delete succeeds and the cascade removes the grade with no "changed" refusal. Very unlikely (5 s, admin only, another tab), and money is safe (make-ups take no payments: `no_fee`; the id list still guards a payment). Fix options: accept and note it, or have the Undo re-read the detail first and refuse when grade count > kept_count. The kept grades copied in by the add itself ARE meant to go.
2. **R2-02 stop-gap turns every second-step refusal into a Retry that can never work.** `StarEventsTab.jsx:522-523` maps anything except ok / no_access / not_allowed to `{ status: 'error' }`. If the registration step really answers `stale` (someone else changed the event) or `finished`, Retry re-sends the same `detailsBackVersion` and fails again forever, instead of the old "changed - reload" banner (`UNDO_STALE`). Network failures are the case it was written for; consider mapping `stale / not_found / finished / invalid` through unchanged (they hit the existing `UNDO_STALE` branch at line 584) and only unknown statuses to `error`. Gone anyway when 0038's one-step function lands.
