G3 · Choice — Undo after restoring a “Duplicate copy”

  • What the database does (checked in 0006_star_testing.sql): “Keep this one” in the compare box withdraws the other row with reason duplicate_copy (star_resolve_duplicate, 18p) — the Removed group tags it “Duplicate copy”, line “duplicate copy Oct 21 by Jeffrey”. Restore (star_restore_candidate, 18s, ~line 4565) sets it active and clears withdrawn_reason, then checks duplicates again — if the two still match, both rows come back flagged “Possible duplicate”. The Undo G3 adds would call star_withdraw_candidate (18r), which always sets reason withdrawn: the row goes back to Removed tagged “Removed” (line “withdrawn Oct 28 by Jeffrey”), not “Duplicate copy”, and the duplicate flag is cleared.
  • OPTION A — no Undo after restoring a duplicate copy: the toast is “Ethan Lopez restored” with no button (as today). Every other Restore gets Undo. To put it back, the admin uses the compare box again (Review → Keep this one), which marks it “Duplicate copy” properly. + never puts a wrong tag on a row. − one Restore without Undo (an exception to rule 1.4).
  • OPTION B — Undo still offered: it withdraws the row again, and it comes back as “Removed”. + every Restore has Undo. − the reason is lost: the row no longer says it was a duplicate copy.
  • Without a migration: both A and B work with today’s functions (A needs no database call; B uses star_withdraw_candidate as is). Neither can bring back “Duplicate copy” through the withdraw function. PROPOSAL (option C, not drawn): Undo could instead call star_resolve_duplicate (keep the partner, withdraw this one) — that writes duplicate_copy again with no migration, but only while the pair is flagged “Possible duplicate” again after Restore, and the app needs the partner’s id and version from the reloaded list. If they no longer match, it would fall back to A or B.
  • Recommendation: A (simplest and never mislabels a row).
